# Project controls

Select only controls that address the project's actual or imminent work. Favor a single coordinator with AI support when that matches the user's briefing; do not assume a multi-person approval hierarchy.

## Folder selection

Use purpose and retrieval needs before file format. Two possible starting arrangements are:

```text
Project/
  AGENTS.md
  Project Guide.md
  Document Log.md
  Received/
  Working/
  Issued/
```

```text
Project/
  AGENTS.md
  Project Guide.md
  Document Log.md
  Customer/
  Suppliers/
  Internal/
```

These are alternatives, not required templates. In the second arrangement, add Received and Issued under the relevant party as needed. Create supplier-named folders only for known suppliers. If the work has no external exchanges, an internal working area may be sufficient. Keep governing documents at the root unless an established project convention provides a better location.

| Condition | Useful response |
|---|---|
| Incoming technical or commercial material | Preserve received originals and their covering messages together or through clear references. |
| Multiple parties with repeated exchanges | Add party subdivisions, keeping each exchange's provenance clear. |
| Internal pricing or sensitive discussion | Use an internal working location and separate recipient-facing copies. |
| Several substantial subjects | Add topic folders once they aid retrieval; do not prebuild every possible discipline. |
| Several rounds of work | Add history beside the relevant working family and identify selected versions in the guide. |
| A complete sent package | Preserve its exact contents and transmission evidence; do not later edit that set. |
| Native files with linked dependencies | Preserve their usable relative structure and associated exports. |

Do not duplicate originals merely to satisfy two classification schemes. An unchanged file may legitimately belong to multiple complete historical exchange packages. Matching bytes do not make those exchange records interchangeable.

## Proportionate additional records

| Recurring need | Possible record | When to defer |
|---|---|---|
| Questions, assumptions and actions span several rounds or parties | One combined issue and decision register | A few open matters fit clearly in the guide. |
| Many requirements need individual evidence | Requirements/compliance table | No compliance demonstration is required or the source is short and unambiguous. |
| Offers differ in scope, exclusions or pricing basis | Supplier comparison or reconciliation | Only one straightforward offer exists. |
| Releases use differing material assumptions or cost sources | Brief basis statement with each relevant release | The actual release and references already make the basis clear. |
| The covering message does not identify an exact package clearly | Compact issue/receipt record | The saved message, attachments and diary already answer the retrieval question. |

Do not create each record as an empty form. Introduce it when real content and a maintenance purpose exist. An analytical output, such as a pricing comparison, need not become a separate governance system.

## Multi-party questions and assumptions

For projects involving a customer, intermediary and suppliers, distinguish:

- What the customer requires or has agreed.
- What each supplier offers, excludes or has confirmed.
- What the intermediary has chosen provisionally and why.
- What has actually been communicated to each party.

One party's answer does not automatically settle the other relationship. Internal pricing decisions need not be disclosed in full, but assumptions affecting the offered scope or commitments need an explicit disposition before release: clarify, qualify, resolve, or deliberately retain with the user's decision recorded.

For a material live issue, use a stable short reference and capture only useful fields: subject/item, source, relevant party positions, current working decision, next action or party awaited, affected outputs, and any known date. A stable tag already used in source documents may be enough. Do not require every field for every issue or create separate registers for questions, risks, assumptions and decisions by default.

Distinguish answer received, decision made, communication sent and consequences incorporated. A changed requirement may affect supplier instructions, estimates, pricing and a customer proposal. Identify the actual affected outputs; update those within scope and mark the rest as awaiting update. Preserve earlier issues. A partial reply closes only what it resolves.

Temporary assumptions should have a permitted purpose and a confirmation or replacement trigger when known. A quotation assumption is not automatically an instruction to execute. Unknown triggers should remain explicit rather than being given invented expiry dates.

## Versions and exchanges

Keep the following meanings distinct:

- **Received original:** the external party's actual file and accompanying message.
- **Working version:** an editable interpretation, calculation, consolidation or draft.
- **Selected basis:** the version or set currently chosen for a stated purpose, possibly with unresolved qualifications.
- **Issued version:** the exact files actually sent, supported by transmission evidence.

Preserve external document IDs, revision labels, original names and package relationships. For internal work, choose a simple identity plus revision/date convention that distinguishes materially different versions, including same-day versions when necessary. Do not make a new formal revision for every formatting edit or rename supplier documents to imply issuer approval.

A later receipt may replace a whole package, one member, selected answers or nothing at all. Establish its scope from the contents and correspondence. A missing member is not automatically carried forward; record the source and grounds for any assembled working set. Preserve complete received packages where they exist without calling a reconstructed set an original receipt.

For an actual issue, retain the exact package, recipient, date, purpose and sending evidence. A file saved under Issued is not itself proof of sending. Record prepared-but-unsent packages as drafts. Keep internal cost notes, hidden comments and other unintended content out of recipient copies when preparing them.

Hashes can establish file identity when needed; they are not required for every entry and do not establish technical correctness, approval or redundancy of context.

## Daily use and handover

For a user maintaining records with AI, make maintenance part of each substantive task: update the working state, note the material event, and refresh guide pointers when needed. Do not require an extra reporting ceremony.

If multiple people or AI sessions can edit the same files, agree a simple ownership or sequencing convention. Do not resolve a synchronization conflict by silently choosing the newest file. Preserve competing evidence and reconcile the meaningful differences before relying on a disputed basis.

When a project finishes, record the outcome, final issued outputs and any remaining obligations in the existing guide and diary. Keep the final evidence retrievable. Archiving a project does not constitute a backup, and no retention period or deletion policy should be invented.
